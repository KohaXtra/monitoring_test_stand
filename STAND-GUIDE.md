# Как устроен стенд — подробная шпаргалка

Цель файла — чтобы ты мог рассказать путь любой точки на графике и любой строки
в логах: откуда она взялась, через что прошла, где лежит, как её достать и что
будет, если звено сломается.

Готовые формулы (RPS, доля ошибок, p95, topk, Expressions) — на дашборде
«PromQL и LogQL: примеры», теория к ним — в [THEORY.md](THEORY.md). Здесь только
устройство и «ориентировочные» запросы, чтобы убедиться, что данные есть.

---

## 0. Общая картина

В стенде три независимых потока данных и одна витрина:

```
                 ┌──────────────── ПОТОК 1: запросы ────────────────┐
  k6 ──HTTP──> nginx:80 ──proxy──> app:8000 (FastAPI)
                  │ stdout             │ stdout          │ /metrics
                  ▼                    ▼                 ▼
             [docker: логи контейнеров]            [текст с метриками]
                  │                                      │
   ПОТОК 3: логи  │                     ПОТОК 2: метрики │ (pull, каждые 15s)
                  ▼                                      ├────────────────┐
     Alloy: discovery.docker                   Alloy: prometheus.scrape   Prometheus
            → relabel → source.docker                 → remote_write     (свой scrape,
            → process → loki.write                    │                   хранит 6h)
                  │                                   ▼                      │
                  ▼                                 Mimir                    │
                 Loki                          (долгое хранение)             │
                  │                                   │                      │
                  └──────────────┬────────────────────┴──────────────────────┘
                                 ▼
                         Grafana:3000 — три датасорса: Loki, Mimir, Prometheus
```

Ключевая мысль: **приложение ничего никуда не отправляет.** Оно только пишет
строки в stdout и держит открытой страницу `/metrics`. Всё остальное делают
сборщики: они сами приходят за данными (pull). Если сборщик упал, приложение
этого не заметит, а данные просто перестанут появляться. Это прямой мостик
к требованию про сборщики: «мониторинг стоит, а данных нет».

Все контейнеры в одной docker-сети `monitoring`, поэтому обращаются друг к другу
по имени сервиса (`app:8000`, `loki:3100`). С хоста — через проброшенные порты
(`localhost:8080`, `localhost:3000`…).

| Сервис | Порт на хосте | Роль |
|---|---|---|
| nginx | 8080 | вход для пользовательского трафика |
| app | 8000 | FastAPI; напрямую — для `/chaos` и `/metrics` |
| k6 | — | генератор нагрузки (профиль `load`) |
| alloy | 12345 | сборщик: метрики → Mimir, логи → Loki |
| prometheus | 9090 | второй сборщик + локальное короткое хранилище |
| mimir | 9009 | долгое хранилище метрик |
| loki | 3100 | хранилище логов |
| node-exporter | 9100 | метрики хоста (CPU, память, диск) |
| grafana | 3000 | витрина, admin/admin |

## 1. Поток 1 — путь HTTP-запроса

### 1.1. k6 → nginx

`monitoring/k6/load.js`. Executor `constant-arrival-rate`: k6 старается
выдерживать **20 запросов в секунду** независимо от того, как быстро отвечает
сервер. Если ответы тормозят, он поднимает больше виртуальных пользователей
(до `maxVUs: 200`).

Почему именно так: при executor «N пользователей в цикле» медленный сервер
автоматически получает меньше запросов, и нагрузка сама падает во время
инцидента. С постоянной частотой RPS на графике стоит ровно, и видно, что
меняется именно латентность и ошибки, а не трафик.

Смесь запросов (примерно):

| Доля | Запрос | Зачем |
|---|---|---|
| 60% | `GET /items/<0..999>` | основная ручка, на неё действует ломалка |
| 20% | `GET /hello/user<0..49>` | вторая ручка с параметром в пути |
| 10% | `GET /` с `Host: api.learnnginx.com` | vhost «апишка» |
| 8% | `GET /` с `Host: docs.learnnginx.com` | vhost «дока» |
| 2% | `GET /does-not-exist` | фоновые 404 |

k6 идёт на `http://nginx` — по имени сервиса внутри сети.

### 1.2. nginx → app

`monitoring/nginx/nginx.conf`:

1. Для каждого запроса nginx генерирует `$request_id` (32 hex-символа).
2. Проксирует в `upstream app` → `app:8000`, прокидывая заголовки:
   - `Host` — чтобы приложение видело vhost (`main.py` ветвится по нему);
   - `X-Request-ID: $request_id` — сквозной идентификатор;
   - `X-Forwarded-For` — реальный адрес клиента.
3. Когда ответ вернулся, пишет **одну JSON-строку** в `/dev/stdout`.
4. `/metrics` и `/chaos` снаружи закрыты (`return 404`): служебные ручки не
   отдаются через публичный вход. Поэтому ломалка вызывается напрямую на
   `localhost:8000`.

Поля лога nginx и что они значат:

| Поле | Что это |
|---|---|
| `request_id` | тот же id, что уйдёт в приложение |
| `vhost` | значение `$host` |
| `uri` | путь **без** query и **с** конкретным ID (`/items/123`) — много значений |
| `status` | код ответа клиенту |
| `request_time` | полное время запроса глазами nginx: от первого байта запроса до отправки ответа |
| `upstream_response_time` | сколько отвечал upstream (приложение). Строка, потому что при ретраях бывает `"0.01, 0.02"`, а при ошибке соединения — `"-"` |
| `bytes_sent` | размер тела ответа |

`escape=json` в `log_format` экранирует кавычки и спецсимволы: без него кривой
User-Agent ломает JSON, и `| json` в Loki на такой строке падает.

Материал для разговора: `request_time − upstream_response_time` — это время,
которое съел сам nginx и сеть до клиента. Если растёт `request_time`, а
`upstream_response_time` нет, значит, тормозит не приложение.

### 1.3. Внутри app

`main.py`, порядок обработки запроса:

```
запрос → middleware access_log (внешний слой)
           → middleware instrumentator (считает метрики)
              → роутинг → хендлер
           ← ответ / исключение
         ← access_log пишет JSON-строку, ставит X-Request-ID в ответ
```

`access_log` зарегистрирован **после** `instrumentator.instrument(app)`,
поэтому в Starlette он оказывается внешним слоем (последний добавленный —
снаружи). Это важно для `/boom`:

1. Хендлер бросает `RuntimeError`.
2. Instrumentator ловит его, записывает в метрики статус `500` и
   пробрасывает дальше.
3. `access_log` ловит, пишет лог с `status: 500, level: error` и сам
   возвращает клиенту JSON 500.

В итоге одно и то же исключение видно и в метриках, и в логах.

Поля лога приложения:

| Поле | Откуда |
|---|---|
| `request_id` | из `X-Request-ID` (от nginx) или новый `uuid4`, если пришли напрямую на :8000 |
| `level` | вычисляется из статуса: ≥500 → error, ≥400 → warning, иначе info |
| `route` | **шаблон** маршрута из роутера (`/items/{item_id}`), а не путь. Если маршрут не найден — `none` |
| `path` | фактический путь с ID |
| `status`, `duration_ms` | итог и время внутри приложения |

Запросы к `/metrics` не логируются: их делают сборщики каждые 15 секунд, и
в логах был бы только шум.

Access-лог самого uvicorn выключен (`--no-access-log` в `Dockerfile`), иначе
каждый запрос давал бы две строки: одну текстовую от uvicorn и одну нашу.

### 1.4. Ломалки

Глобальный словарь `chaos = {"delay": 0.0, "error_rate": 0.0}` живёт
в памяти процесса. Он действует только на `/items/{item_id}`:

```
задержка = случайно(5..50 мс)  +  delay × случайно(0.5..1.5)
с вероятностью error_rate → HTTPException(500)
```

- Базовые 5–50 мс нужны, чтобы перцентили не были плоской линией.
- Разброс `0.5..1.5` делает деградацию реалистичной: не все запросы
  тормозят одинаково.
- `asyncio.sleep`, а не `time.sleep`: асинхронный сон не блокирует event
  loop, поэтому тормозит только `/items`, а `/hello` и `/` отвечают как раньше.
  С `time.sleep` лёг бы весь сервис.

Управление: `POST /chaos?delay=0.5&error_rate=0.3`; без параметров всё
сбрасывается в ноль. Так как состояние хранится в памяти, после рестарта
контейнера `app` ломалка тоже сбрасывается.

## 2. Поток 2 — метрики

### 2.1. Что отдаёт приложение

`GET localhost:8000/metrics` — текстовая страница. Её формирует
`prometheus_fastapi_instrumentator` поверх `prometheus_client`. Это
**текущее** состояние счётчиков, истории в ней нет. Историю строит тот, кто
периодически забирает страницу и складывает значения с метками времени.

Основные метрики:

| Метрика | Тип | Лейблы | Смысл |
|---|---|---|---|
| `http_requests_total` | counter | `handler`, `method`, `status` | сколько запросов обработано с момента старта процесса |
| `http_request_duration_seconds` | histogram | `handler`, `method` | латентность по ручкам, бакеты 10мс…10с (настроены в `main.py`) |
| `http_request_duration_highr_seconds` | histogram | — | латентность всего сервиса, много бакетов, без разбивки по ручкам |
| `http_request_size_bytes`, `http_response_size_bytes` | summary | `handler` | размеры (по Content-Length) |
| `*_created` | gauge | как у родителя | время создания серии — служебное, для дашбордов не нужно |
| `python_*`, `process_*` | разные | — | рантайм: GC, память, CPU, открытые файлы |

**Counter** только растёт и обнуляется только при рестарте процесса. Сам по
себе он бесполезен (число «10 033» ни о чём не говорит), смысл появляется
у скорости его роста — отсюда `rate()`.

**Histogram** — это не одна метрика, а набор серий:

```
http_request_duration_seconds_bucket{handler="/items/{item_id}", le="0.025"}  4183
http_request_duration_seconds_bucket{handler="/items/{item_id}", le="0.05"}   9672
...
http_request_duration_seconds_bucket{handler="/items/{item_id}", le="+Inf"}   10033
http_request_duration_seconds_sum{...}    ← сумма всех длительностей
http_request_duration_seconds_count{...}  ← число наблюдений (= bucket le="+Inf")
```

Бакеты **накопительные**: `le="0.05"` значит «запросов, уложившихся в
≤ 50 мс», и включает все меньшие бакеты. Каждый бакет — это counter.

Почему заменены бакеты: по умолчанию у библиотеки `0.1, 0.5, 1`. Наша ручка
отвечает за 5–50 мс, и все запросы попадали бы в первый бакет,
`histogram_quantile` выдавал бы примерно «где-то до 100 мс». Точность
перцентиля ограничена шириной бакета, куда он попал. Цена каждого лишнего
бакета — ещё одна серия **на каждое сочетание лейблов**, так что бакеты
выбираются под реальный диапазон латентности, а не «побольше».

Почему `should_group_status_codes=False`: иначе статус был бы `5xx`, и
500 от 503 не отличить. Кардинальность от этого почти не растёт, потому что
кодов немного.

**Лейбл `handler` — это шаблон маршрута**, а не путь. Если бы там был
`/items/123`, то на 1000 ID получилась бы 1000 серий × бакеты × методы. Это
та же проблема кардинальности, что и в Loki. Запросы в несуществующие
маршруты сводятся в `handler="none"` (`should_group_untemplated=True`).

### 2.2. Alloy: scrape → remote_write → Mimir

`monitoring/alloy/config.alloy`, верхняя половина. Alloy — это граф
компонентов. Каждый компонент что-то делает и передаёт результат дальше через
`forward_to`. Граф можно посмотреть вживую: http://localhost:12345.

```
prometheus.scrape "fastapi"        ─┐
prometheus.scrape "node_exporter"  ─┴─ forward_to → prometheus.remote_write "mimir" → HTTP POST mimir:9009/api/v1/push
```

Что происходит каждые 15 секунд (`scrape_interval`):

1. `prometheus.scrape` делает `GET http://app:8000/metrics`.
2. Парсит текст и к каждой серии добавляет лейблы цели:
   - `job` — из конфига (`fastapi` / `node_exporter`);
   - `instance` — адрес цели (`app:8000`).
3. Дополнительно генерирует **синтетические** серии про саму попытку скрейпа:
   - `up` (1 — ответил, 0 — нет);
   - `scrape_duration_seconds`;
   - `scrape_samples_scraped` и другие.

   Их нет на странице `/metrics`, их создаёт сборщик. Именно по ним строится
   мета-мониторинг.
4. Сэмплы (серия + значение + время) уходят в `remote_write`.
5. `remote_write` сначала пишет сэмплы в WAL на диске, из него батчами шлёт
   в Mimir и повторяет при ошибках. Если **Mimir** недоступен, данные ждут
   в WAL и доотправляются после восстановления (в пределах лимитов). Если
   недоступен **сам Alloy**, WAL не поможет: скрейпить некому (см. раздел 7).

`job` для node_exporter задан явно. Без него лейбл был бы
автоматическим (`prometheus.scrape.node_exporter`), и переменная дашборда по
`job` выглядела бы криво.

### 2.3. Mimir внутри

`monitoring/mimir/mimir.yml`. `target: all` — монолит: все компоненты Mimir
работают в одном процессе. В проде это отдельные сервисы, но путь данных тот же:

```
ЗАПИСЬ:  push → distributor → ingester (держит свежие данные в памяти + WAL на диск)
                               └─ раз в ~2 часа режет блок → /data/blocks (object storage; здесь filesystem)
                                                              └─ compactor склеивает блоки, чистит по ретеншну
ЧТЕНИЕ:  Grafana → query-frontend → querier ─┬─ ingester (свежее)
                                              └─ store-gateway (старые блоки из storage)
```

- `replication_factor: 1` и `kvstore: inmemory` — одна копия, кольцо
  (ring) в памяти. В проде ingester'ов несколько, каждая серия пишется в 3,
  а ring живёт в memberlist или consul.
- `multitenancy_enabled: false` — все данные в одном тенанте `anonymous`.
  При `true` каждый запрос обязан нести заголовок `X-Scope-OrgID`.
- Grafana ходит по адресу `http://mimir:9009/prometheus` — Mimir отдаёт
  Prometheus-совместимый API под префиксом `/prometheus`. Поэтому тип
  датасорса — `prometheus`: язык запросов тот же PromQL.

### 2.4. Prometheus

`monitoring/prometheus/prometheus.yml` + флаги в compose.

- Скрейпит **те же** цели (`app:8000`, `node-exporter:9100`) плюс самого себя.
  Скрейп он делает независимо от Alloy, так что приложение опрашивают дважды
  за 15 секунд. Для `/metrics` это нормально: ответ дешёвый, а значения
  counter'ов одни и те же.
- Хранит у себя в TSDB (`/prometheus`, volume `prometheus-data`) **6 часов**
  (`--storage.tsdb.retention.time=6h`).
- В Mimir **не пишет — это решение, а не недоработка.** Alloy уже шлёт туда
  серии с тем же набором лейблов. Если добавить `remote_write` и
  в Prometheus, Mimir получит две копии одной серии от двух отправителей:
  будут конфликты «duplicate sample / out of order», а часть данных
  отбросится. Правильно делается через разные `external_labels` у отправителей
  (тогда в запросах придётся фильтровать или дедуплицировать) или через
  HA-дедупликацию Mimir (лейблы `cluster`/`__replica__`). Для стенда проще
  развести роли.

Что это даёт на демо: за последний час один и тот же запрос в датасорсах
Prometheus и Mimir выдаёт почти одинаковые кривые. Небольшая разница есть,
потому что скрейпы происходят в разные моменты. Если сдвинуть окно дальше
6 часов, в Prometheus данных нет, а в Mimir есть.

Цели Prometheus: http://localhost:9090/targets.

### 2.5. node-exporter

Метрики **хоста**, а не контейнера: смонтированы `/proc`, `/sys` и `/`
хоста в режиме только чтения, плюс `pid: host`. Отдаёт `node_cpu_seconds_total`,
`node_memory_*`, `node_filesystem_*` и т. п. Это данные для импортированного
дашборда Node Exporter Full (адаптированный 1860).

`--collector.filesystem.mount-points-exclude` выкидывает виртуальные ФС
(`/sys`, `/proc` и т. д.), иначе появились бы десятки бесполезных серий.
`$$` в compose — экранирование `$`.

`network_mode: host` обязателен для сетевых графиков: `/proc/net/dev` показывает
сетевой namespace **читающего процесса**, и `pid: host` тут не помогает. В
bridge-сети node-exporter видел бы только свои `eth0` и `lo`, а скорости
интерфейсов (`/sys/class/net`) — хостовые, поэтому «Network Saturation» была
пустой. Prometheus и Alloy ходят к нему на `host.docker.internal:9100`
(`extra_hosts: host-gateway`), а метка `instance` принудительно оставлена
`node-exporter:9100`, чтобы не рвались серии и переменные дашборда.

## 3. Поток 3 — логи

### 3.1. Откуда логи берутся

Приложение и nginx пишут в **stdout**. Docker (драйвер по умолчанию
`json-file`) сохраняет каждую строку у себя вместе с меткой времени и отдаёт
их через Docker API — так же, как это делает `docker logs app`. Файлов логов
в стенде никто не монтирует.

### 3.2. Alloy: четыре компонента

`monitoring/alloy/config.alloy`, нижняя половина:

```
discovery.docker  ──targets──>  loki.source.docker  ──>  loki.process  ──>  loki.write → loki:3100
                                      ▲
discovery.relabel ───rules────────────┘
```

Alloy смотрит в Docker через смонтированный сокет
`/var/run/docker.sock` (в compose, `:ro`).

**1. `discovery.docker`** опрашивает Docker API: какие контейнеры запущены.
Для каждого выдаёт «цель» с метаданными `__meta_docker_container_name`,
`__meta_docker_container_label_*` и т. д. Лейблы с префиксом `__` —
служебные, в Loki они не попадут, если их явно не переименовать.

**2. `discovery.relabel`** — правила переименования **метаданных**:
- лейбл compose `com.docker.compose.service` → `service` (`app`, `nginx`, …);
- имя контейнера `/app` → `container` = `app` (регулярка отрезает `/`).

Здесь `targets = []`, потому что компонент используется только как
контейнер правил: его `.rules` передаются в `loki.source.docker`, и тот
применяет их сам. Так рекомендует дока: `loki.source.docker` нужны исходные
`__meta_*`, чтобы найти контейнер, и прогонять цели через `.output` нельзя.

**3. `loki.source.docker`** для каждой цели подписывается на поток логов
контейнера через API и превращает каждую строку в запись «лейблы +
время + текст». Без шага релейблинга все логи ушли бы одним безымянным
потоком.

**4. `loki.process`** обрабатывает **содержимое строки**:
- `stage.match {service="app"}` — следующие шаги применяются только к логам
  приложения;
- `stage.json` достаёт поле `level` из JSON во временное хранилище;
- `stage.labels` повышает `level` до лейбла потока.

Остальные поля (`request_id`, `route`, `status`, `duration_ms`) **остаются
просто текстом строки**.

**5. `loki.write`** — батчами шлёт POST в `loki:3100/loki/api/v1/push`,
с ретраями.

Граница, которую спросят: **relabel** работает с метаданными цели до
того, как прочитана хоть одна строка. **stage** работает с каждой строкой
после чтения. Один раз на контейнер против одного раза на строку.

### 3.3. Лейблы, стримы и почему только три лейбла

В Loki **стрим** — это уникальный набор лейблов. У нас примерно так:

```
{service="app",   container="app",   level="info"}
{service="app",   container="app",   level="warning"}
{service="app",   container="app",   level="error"}
{service="nginx", container="nginx"}
{service="loki",  container="loki"}
... по одному на остальные контейнеры
```

Итого чуть больше десятка стримов. Loki индексирует **только лейблы**,
содержимое строк не индексируется: оно сжимается кусками (chunks) по
стримам.

Поэтому:
- `{service="app", level="error"}` — поиск по индексу, дешёвый: Loki сразу
  знает, какие чанки читать;
- `{service="app"} |= "d33827e0"` — Loki берёт все чанки стрима за
  окно, распаковывает и просматривает строки. Работает, но стоимость растёт
  с объёмом, а не с числом совпадений.

Если бы `request_id` стал лейблом, **каждый запрос создавал бы новый стрим**:
20 RPS → 72 000 стримов в час, в каждом по одной строке. Индекс раздувается,
чанки крошечные, ingester упирается в лимиты стримов. Поэтому в лейблах —
то, чего мало и что конечно, а `request_id` — поле внутри строки,
достаётся через `| json`.

То же самое с nginx: `uri` — это `/items/123`, значений тысячи. Лейблом он
быть не может, и даже группировать по нему в запросе плохо. Группировать надо
по `route` из лога приложения, где уже стоит шаблон.

### 3.4. Loki внутри

`monitoring/loki/loki.yml`. Та же схема, что у Mimir: монолит,
filesystem, одна реплика, ring в памяти.

- `schema_config`: `store: tsdb`, `schema: v13`, `period: 24h` — текущая
  рекомендуемая схема индекса, новый индекс-файл раз в сутки. `from` —
  дата, с которой действует схема. Схемы меняют, добавляя новую запись
  с будущей датой, старую не трогают.
- `retention_period: 168h` + `compactor.retention_enabled` — логи живут
  7 дней. Удаляет их именно compactor: без `retention_enabled` лимит
  ретеншна ничего не делает.
- `auth_enabled: false` — один тенант (`fake`), как `multitenancy_enabled:
  false` у Mimir.

Путь: push → distributor → ingester (копит строки в чанки по стримам, держит в
памяти и WAL) → сброс чанков в `/loki/chunks`, индекс в tsdb →
чтение через querier.

## 4. Grafana — витрина

### 4.1. Provisioning

При старте Grafana читает `/etc/grafana/provisioning/` (смонтирована
папка `monitoring/grafana/provisioning`):

- `datasources/*.yml` — три датасорса с **фиксированными uid** (`mimir`,
  `prometheus`, `loki`). Фиксированный uid важен для дашбордов как код: JSON
  дашборда ссылается на датасорс по uid, и на чистом стенде он найдётся.
  Иначе uid генерируется случайно, и выгруженный дашборд на другой машине
  «не видит» датасорс.
- `editable: false` — датасорс нельзя поменять из UI: источник правды — файл.
- `timeInterval: "15s"` у Prometheus-датасорсов — подсказка Grafana, что
  реже 15 секунд точек нет. От этого зависит, чему равен `$__rate_interval`
  (его минимум завязан на интервал скрейпа).
- `dashboards/dashboards.yml` — провайдер: раз в 30 секунд перечитывает JSON
  из `/etc/grafana/provisioning/dashboards`. Там лежат три дашборда как код:
  `red.json` (RED), `examples.json` («PromQL и LogQL: примеры»),
  `node-exporter.json` (адаптированный 1860). Включён `allowUiUpdates: true`:
  правки из UI сохраняются, но при изменении JSON-файла главным снова
  становится он. Цикл такой: правишь в UI → Export → JSON → кладёшь в файл.
  В проде `allowUiUpdates` выключают: дашборд меняется только через ревью.

### 4.2. Derived fields (связка логов)

В `datasources/loki.yml`: регулярка `"request_id":\s*"(\w+)"` ищет id в
каждой строке. `\s*` нужен потому, что в логе nginx после двоеточия пробела
нет, а `json.dumps` в приложении его ставит. Найденное значение становится
ссылкой на запрос `{service=~"app|nginx"} |= "<id>"`.

В Explore: раскрываешь строку лога → поле `request_id` → клик → видишь
строку nginx и строку приложения по одному запросу. Сравни `request_time`
у nginx и `duration_ms` у приложения.

### 4.3. Какой датасорс для чего

| Вопрос | Куда |
|---|---|
| RPS, ошибки, латентность по ручкам, история | Mimir |
| То же за последние часы, «локально» | Prometheus |
| Что именно происходило в конкретных запросах | Loki |
| Метрика из логов nginx (время ответа по vhost) | Loki, metric query |
| Метрика и лог-метрика на одном графике | датасорс `-- Mixed --` |

## 6. Как проверить каждое звено

Идти слева направо: первое звено, где данных нет, и есть поломка.

**Запрос проходит:**
```bash
curl -i -H 'Host: api.learnnginx.com' localhost:8080/   # 200, "Это апишка", заголовок X-Request-ID
```

**Приложение пишет лог и метрики:**
```bash
docker logs --tail 3 app
docker logs --tail 3 nginx
curl -s localhost:8000/metrics | grep '^http_requests_total'
```

**Сборщики видят цели:**
- Alloy: http://localhost:12345 — список компонентов со статусом. Клик по
  имени → страница компонента (`/component/prometheus.scrape.fastapi`):
  сверху health компонента, ниже Arguments, Exports и **Debug Info**.
  - `prometheus.scrape.*` → Debug Info → блок `target`: `url`, `health`
    (`up`/`down`), `last_scrape`, `last_scrape_duration`. Поле `last_error`
    появляется только при ошибке скрейпа: чтобы увидеть, сделай
    `docker compose stop app` и через 15–30 с обнови страницу.
  - `loki.source.docker.containers` → Debug Info → `targets_info` по одному
    на контейнер: `id`, `last_error`, `labels`. Имя контейнера ищи в
    `__meta_docker_container_name`.
  - Вкладка **Graph** — граф компонентов со связями `forward_to`.
- Prometheus: http://localhost:9090/targets — все `UP`.

**Хранилища получают данные:**
```bash
# Mimir
curl -s localhost:9009/prometheus/api/v1/query --data-urlencode 'query=up'
# Prometheus
curl -s localhost:9090/api/v1/query --data-urlencode 'query=up'
# Loki: какие service есть
curl -s localhost:3100/loki/api/v1/label/service/values
```

**Grafana видит хранилища:** Connections → Data sources → каждый → Test.

**Ориентировочные запросы в Explore** (просто «данные есть»):
- Mimir/Prometheus: `up`, затем `http_requests_total` — смотришь сырые
  counter'ы и видишь, что они растут лесенкой.
- Loki: `{service="app"}`, затем `{service="app", level="error"}`, затем
  `{service="nginx"} | json` — у строк появляются поля.

### Типичные поломки

| Симптом | Где смотреть |
|---|---|
| В Mimir нет `job="fastapi"` | Alloy UI → ошибка скрейпа (не резолвится имя? контейнер `app` упал?) |
| `up == 0` | цель есть в конфиге, но не отвечает: `docker compose ps`, `docker logs app` |
| Серии нет вообще (даже `up`) | цели нет в конфиге сборщика — «невидимый» таргет |
| В Loki нет новых строк | `docker logs alloy` — ошибки `loki.write`; жив ли loki |
| Все логи одним потоком без `service` | не применились `relabel_rules` |
| Данные есть в Prometheus, но нет в Mimir | проблема в пути Alloy → Mimir, а не в приложении — хороший пример для разговора |
| Графики пустые после `down -v` | удалены volume'ы, истории нет — это ожидаемо |

## 7. Сценарии для демо

### Сломать сервис (основное требование)
```bash
docker compose --profile load up -d k6                       # трафик
curl -X POST 'localhost:8000/chaos?error_rate=0.3'            # 30% 500-к на /items
curl -X POST 'localhost:8000/chaos?delay=0.5'                 # латентность /items растёт, остальные ручки нет
curl -X POST 'localhost:8000/chaos'                           # починить
```

Что должно быть видно:
- в метриках растёт доля `status="500"` у `handler="/items/{item_id}"`;
- в Loki появляется стрим `level="error"`;
- при `delay` сдвигаются верхние бакеты гистограммы, а у `/hello` ничего не
  меняется. Это доказательство, что event loop не заблокирован.

Учти задержку: скрейп раз в 15 секунд плюс окно `rate()`, поэтому
график реагирует через 30–60 секунд. На демо сломай и проговори, что
делаешь, пока ждёшь, — это нормально и честно.

### Сломать сбор (требование про сборщики)
```bash
docker compose stop node-exporter   # up{job="node_exporter"} → 0 в Mimir и Prometheus
docker compose stop alloy           # в Mimir и Loki перестают приходить данные, в Prometheus — нет
```

Второй сценарий особенно показателен. Сервис работает, Prometheus показывает
всё хорошо, а в Mimir тишина: `up` не становится нулём, серии просто
**обрываются**. Тот, кто ставит алерт `up == 0` в Mimir, этого не заметит:
нужен `absent()` или мониторинг самого сборщика.

После `docker compose start alloy` поведение двух потоков **разное** (проверено
на стенде: Alloy остановлен на 90 секунд):
- **метрики за простой потеряны навсегда.** В Mimir за 4 минуты 10 сэмплов
  `up`, в Prometheus 16. Pull-модель: `/metrics` отдаёт только текущее
  состояние, и скрейп, который не сделали, задним числом не сделать;
- **логи догрузились без дыры** — ровно 600 строк nginx на каждое 30-секундное
  окно, включая время простоя. Docker сам хранит stdout контейнера
  (`json-file`), а Alloy запомнил позицию чтения и дочитал хвост.

Отсюда вывод для разговора о полноте: у логов буфер находится у источника
(docker, файл), у pull-метрик буфера нет. Логи не спасут, если контейнер
пересоздан (`down`/`up`) или сработала ротация docker-логов.

## 8. Понятия, которые стоит уметь объяснить на этом стенде

- **Pull vs push.** Сборщик сам ходит за метриками. Плюсы: сборщик знает,
  что цель жива (`up`); цель не знает, кто её читает; легко запустить второй
  сборщик (у нас Prometheus рядом с Alloy). Логи у нас тоже собираются
  «pull'ом» из Docker API, а в Loki и Mimir данные уходят push'ем.
- **Сэмпл, серия, кардинальность.** Серия — это имя метрики плюс уникальный
  набор лейблов. Число серий = произведение числа значений всех лейблов.
  Каждый бакет гистограммы — отдельная серия.
- **Counter и сброс.** После рестарта `app` counter начинается с нуля.
  `rate()` и `increase()` видят падение и считают его сбросом, а не
  отрицательной скоростью. Проверь сам: `docker compose restart app` и
  посмотри сырой counter и `rate` от него.
- **Staleness.** Если серия исчезла со страницы `/metrics` или цель перестала
  отвечать, Prometheus сразу пишет staleness marker, и график обрывается, а не
  тянет последнее значение. Если маркер записать некому (упал сам сборщик,
  как в сценарии с Alloy → Mimir), запрос ещё до 5 минут (lookback delta)
  подставляет последнее значение, а потом серия пропадает.
- **Почему у Loki отдельная модель данных.** Индексируются только лейблы, а
  метрики из логов считаются на лету при каждом запросе по сырым строкам.
  Поэтому та же цифра из Mimir дешевле: там она уже посчитана при записи.

## 9. Упрощения стенда (честно назвать, если спросят «а в проде?»)

- Mimir и Loki — монолиты с одной репликой и filesystem-хранилищем. В проде
  отдельные компоненты, S3/GCS, репликация ×3, memberlist.
- Нет аутентификации и мультитенантности Mimir.
- У Alloy нет volume: при `stop`/`start` WAL и позиции чтения логов
  сохраняются (они в файловой системе контейнера), а при пересоздании
  (`down`/`up`, смена конфига compose) теряются.
- Alloy получает docker-сокет — это фактически root-доступ к хосту.
  В k8s логи собираются из файлов на ноде или через API kubelet, сокет не
  монтируется.
- Prometheus и Alloy скрейпят одно и то же ради демонстрации. В реальной
  схеме был бы один сборщик на цель.
- Ломалка хранится в памяти одного процесса: при нескольких репликах `app`
  она действовала бы только на ту, куда попал `POST /chaos`.
